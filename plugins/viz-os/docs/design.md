# viz-os: design notes

For people working on the plugin. The skill files never point here: rules an agent needs live in `skills/deck/`.

## Decisions (and why)
| Decision | Why | Where |
|---|---|---|
| The agent writes only `deck.yaml`; one kit draws everything | Style drift in long outputs comes from hand-written HTML/CSS. If design is not in the model's output, it cannot drift. It also saves tokens: the 30-slide MAGeCK deck is about 3,900 words of YAML, against tens of thousands of tokens for hand-written HTML. | `kit/`, `SKILL.md` |
| Rules that long outputs forget are lint checks, not prose | Prose rules decay with output length; a linter does not. The checks: every displayed symbol has a meaning, the ladder order, derived columns have formulas, every working step has its what and why, maths is not typed into prose, text budgets, checkpoint spacing, abbreviations, retired keys. | `scripts/build.py` |
| One expression language for derive, tables, calc, ops, equations, chart functions and `{{text}}` | The formula that computes a number is the formula shown to the learner, so the two cannot disagree; numbers are never typed. | `kit/core.js` |
| Aggregates show their recipe (`mean(x)` → (1/n)Σxᵢ → (8+34+…)/6) | The failure in earlier decks was "x̄ = x̄ = 22.5": a number with no visible logic. | `L.tex` in `core.js` |
| Numbers in worked lines carry their names underneath, once per slide | Anonymous numbers ("0.05152 − 0.009313") were the core complaint about earlier calc pages. Labelling once per slide keeps the clutter down. | `opLabels` in `slides.js` |
| Probe before building: goal, pretest, what they know, which comparison clicks (length only when unsaid) | Prior knowledge decides the entry rung (expertise reversal); a pretest helps memory of the questioned material; anchors make the bridges personal. 3–4 questions keep the reply to one short line. | `probe.md` |
| A `lead` line on each slide ("But…", "So…") | It makes the causal chain visible and catches "and then" gaps. The lint warns when fewer than half the slides have one. | `story.md` §4 |
| One look, flat and square, after proff-viz 5.0.0 | The user asked for the older proff-viz look as the template ("old plugin as template"). Near-black page `#0b0c0e`; content on plates `#171819` with thick grey borders `#565653` and hard offset shadows; heavy Inter headlines, JetBrains Mono tags; one orange `#ff5a36` for the answer and what matters now, never a background. No blur and no backdrop filters, so a phone's Safari draws what Chromium checked. The `theme` key is retired (the lint warns), so every deck looks the same. History: moonlit, then an orange-glow wallpaper, then proff mono grey, then iOS-style glass (1.0.0), then this. | `vizos.css` |
| Series colours blue `#7fb0ff`, mint `#5fdcc4`, magenta `#c274aa`; grey `#b6b4ad` for context | Measured on 2026-10-24 with the CIEDE2000 colour difference (ΔE00; the code was checked against Sharma, Wu & Dalal 2005, pair 1 = 2.0425). Colour blindness was simulated with the Machado, Oliveira & Fernandes (2009) matrices at full severity, in linear RGB. Every pair among the three series and the orange: ≥ 31.5 for normal vision, ≥ 15.9 for protan and deutan (worst: mint vs magenta, deutan), ≥ 10.7 for tritan (blue vs mint). The 2.0 draft's third colour, violet `#c89cf2`, was 2.4 (protan) and 3.8 (deutan) from the blue: nearly the same colour for a red-green colour-blind reader. Magenta was the best third colour in the violet–magenta band of a search over OKLCH (lightness 0.60–0.92, chroma 0.09–0.18, contrast ≥ 4.5:1 on the raised plate `#242526`). Lime and yellow scored a little higher (19.2, 19.1) but were not taken: lime is close in hue to the green "good" colour, and a bright yellow competes with the orange for attention. The weakest pair left is mint vs the context grey (7.7 protan, 6.8 deutan); grey reference lines are also dashed, so they do not rely on colour alone. WCAG contrast on the plate: blue 8.1, mint 10.6, magenta 5.4, orange 5.7, grey 8.6 (all ≥ 4.5:1, so each can carry text). | `vizos.css`, series order in `chart.js`, term colours in `slides.js` |
| Two stages: 1600×900 landscape and 720×1280 portrait | Phones are a main viewing device. One scaled 16:9 stage makes text about 7px on a phone; a portrait stage keeps body text at 16px or more. | `deck.js`, `vizos.css` |
| Content that runs long is zoomed down (never below 70%), and the audit warns below 80% | Robust to slightly-too-long slides without hiding the problem. The fit measures each card's content against the card's own padding, because a grid or flex child can stick out of its card without changing the card's `scrollHeight`; the audit flags any text that spills out of its card. The fit runs again after an answer opens (only ever shrinking, so nothing jumps), and a fit started for a slide already left is dropped. | `fitSlide`, `L.refit`, `L.audit` in `deck.js` |
| The browser check also re-fits every slide with animations on | During 2.0 work the fit was measured while slides were still animating in, so every phone slide shrank to 70% for real viewers. The check, with animations off, saw full size and passed. Now it re-fits each slide live and warns when a viewer would see it shrunk differently. It also opens every predict answer and audits the slide again ("after the answer"). | `scripts/check.py` |
| Contrast is measured on pixels, against a screenshot with the text hidden | Labels over chart marks and over tinted cells are where legibility fails. Per-line fragments avoid false readings from chips beside the text. | `scripts/check.py` |
| YAML 1.2 booleans (`No` stays text) and one-line YAML errors with a fix hint | Both were hit while writing the example deck: `[Yes, about 2×, No, …]` split on commas, `No` became `false`, and a `?` broke a flow map. | `build.py`, `spec.md` |
| Compact headlines (46px), wider visuals (text column 27%) | The user asked for smaller headings and bigger plots. | `vizos.css` |
| Visual first: the linter counts the words on each slide | The user's feedback: slides were text-heavy and the story should come through the visuals. proff-viz's own floor says the same ("the figure is the page": short labels on the figure, ≤ 40 words of labels per step). Limits: about 40 words on an idea slide, ≤ 2 short points beside a visual, titles ≤ 8 words, captions ≤ 20; an idea slide without a visual is warned. Labels inside a chart, flow or parts bar have their own limits. | `build.py` |
| The formula is the figure: each term is named under it | Names sit next to the thing they name, and the same colour links a term to its number in the worked line. Saying it aloud and the code moved behind "+ more", one tap away. | `slides.js` (`termLabels`) |
| `parts` visual: a whole split into named pieces, or one bar per row | Variance = counting part + wobble part was told in tables and algebra; the sizes were never seen. One bar shows a split; rows show how the split changes (the wobble's share as the mean grows). | `slides.js` |
| No formula from nowhere: `from:` and `kin:` on every equation | The user's feedback: formulas appeared out of nowhere. They wanted an idea of how each one is reached (not the full derivation) and how it relates to formulas in other topics. Each equation shows a short chain from a form the learner knows, one move per link (CPM = a percentage counted per million; the Poisson = the binomial with many rare tries), and 1–3 relatives with the same shape elsewhere (run rate, parts per million). On a wide screen the chain is a column beside the formula that flows down and points across into it; on a phone it is a band above. The linter warns when an equation has no `from`. | `slides.js` (`T.equation`), `build.py`, `story.md` §7 |
| Tables one step at a time | The user wanted step-by-step calculation in tables. Step 1 names the given columns and what each holds; then a column (or a row, or a single number) per step. The cells a formula reads are underlined in the colour their symbol wears in the formula, so each number can be followed from the table into the working (signalling plus spatial contiguity). All steps' working shares one grid cell, so the card never changes size between steps. Any computed number can be tapped for its own working. | `slides.js` (`T.table`) |
| Term labels: above the formula for numerators and powers, below for the rest; slide before dropping a row | Labels under a stacked fraction hung on one vertical leader and the lower leader cut through the upper label. Now the side is set by the term's height against the `=` sign, a label slides sideways while its leader still lands inside it, neighbours are pushed left as a group to open a lane, and a label drops a row only when that fails. Wrapped labels shrink to their longest line. The audit flags any label that still has to cross. | `termLabels` in `slides.js` |
| `ops` slides for matrix steps: the row or column being computed is lit, the shape change is named, one row is worked in numbers | The user could not see whether a step ran along rows, down columns or over the whole matrix, or how the data changed shape (counts → ratios → one number per guide). Each step is one operation (`rows`, `cols`, `map`, `dot`, `sort`, `vec`) with its shape before and after. The matrix shows the mechanics only; a chart after it carries the result. | `kit/ops.js`, `spec.md` (Matrix steps) |
| `dist` visual for named distributions | The user wanted distributions shown with their shape and parameters. A `dist` names the family, says what each parameter means, gives the mean and variance with their formulas, and can shade a tail. A slider moves the parameter that is the lesson. | `slides.js`, `chart.js`, `spec.md` (Distributions) |
| Every step says what and why | The old decks showed tables "not really specifying why". `why:` on working slides, `say:` and `why:` on `calc` lines and `ops` steps, and `says:` on computed columns are short and linted, so the reason sits next to the step it explains. | `build.py`, `slides.js`, `ops.js` |
| A worked line must add up by hand | A line's `fmt` used to round the numbers going in as well as the result: 2.648 showed as 3, and "3 × 418^1.22 = 4,291" was off by about 10%. Now `fmt` rounds only the result. The numbers going in get up to 2 extra digits until the shown result follows from them; otherwise the line reads ≈ and the check warns. | `subFmt` in `slides.js`, `L.audit` in `deck.js` |
| Real-method facts come from the code, with the version; numbers come from a seeded script and an independent recompute | Papers and code disagree. MAGeCK 0.5.9.5 computes each guide's p-value from a normal tail (its negative binomial p-value function is commented out), while the paper describes negative binomial p-values. The deck teaches the code and says so. `make_data.py` writes `data.json`; `verify_data.py` recomputes every number with separate code; `check.py` writes `numbers.txt` with every number the slides show. An agent that did not write the deck can compare all three. | `story.md` §11, `examples/mageck-rra/`, `check.py` |
| Chapter shapes and notation chips | The user wanted to see how the data changes type and shape, and to learn the notation. A chapter names the shape it produces, and its divider shows "in → out". The first slide that uses a symbol (Σ, a hat, `x_ij`, Φ) gets a small chip that says what it means. | `slides.js`, `spec.md` |
| Pictures only on request, with no text in them | An image model costs time and tokens and cannot spell labels reliably. `scripts/image.py` runs only when the user asks; the kit draws the labels on top of the picture. | `scripts/image.py`, `spec.md` (Visuals) |

## Evidence behind the story rules
Sources were checked by web search during 1.0.0 work; effect sizes are as reported by those sources.
- **Pretesting / prequestions.** St. Hilaire, Chan & Ahn (2024), *Psychonomic Bulletin & Review*, preregistered meta-analysis: specific effect g = 0.54 (k = 97), general effect g ≈ 0.04 (k = 91). Guessing helps memory of the questioned material, not the rest. Narrative review: Pan & Carpenter (2023), *Educational Psychology Review* 35:97. Hence the pretest is about the core mechanism, and the deck reveals it.
- **Comparison and analogy.** Alfieri, Nokes-Malach & Schunn (2013), *Educational Psychologist* 48(2): case comparison beats single-case study (reported d ≈ 0.50; one summary says 0.60). Bridging analogies and "anchoring intuitions": Clement (1993), *Journal of Research in Science Teaching* 30(10). Hence `bridge` slides with explicit pairs and `breaks`.
- **Concrete to abstract.** Fyfe, McNeil, Son & Goldstone (2014), *Educational Psychology Review* 26: start concrete, fade to abstract. A 2020 review questions how far this carries into advanced science (*Educational Psychology Review*, 10.1007/s10648-020-09581-7). Hence numbers before symbols, without dropping the general form.
- **Prior knowledge.** Expertise reversal effect: Kalyuga, Ayres, Chandler & Sweller (2003), *Educational Psychologist* 38. Hence the probe sets the entry rung and skips known rungs.
- **Names first.** Mayer's pre-training principle: learning improves when the names and characteristics of key concepts come first. Hence the `name` move and `symbols` with meanings.
- **Signalling.** Schneider, Beege, Nebel & Rey (2018), *Educational Research Review* 23 (103 studies): signalling helps retention and transfer, more for low prior knowledge. Hence colour-linked terms, the orange accent and the "Look:" captions.
- **Narrative.** Dahlstrom (2014), *PNAS* 111 (Suppl. 4): narrative raises comprehension and engagement for non-experts. Hence the spine and the but/so chain.
- **Comparing cases, and explaining why.** Comparing two analogous cases helps learners pull out the shared structure and transfer it: Gentner, Loewenstein & Thompson (2003), *Journal of Educational Psychology* 95, 393–408 (comparing two cases beat studying them one at a time). Explaining why a fact holds (elaborative interrogation) and self-explanation were rated moderate utility in Dunlosky et al. (2013), *Psychological Science in the Public Interest* 14(1), doi 10.1177/1529100612453266, with larger benefits when the learner has more prior knowledge. Hence `from:` (why this form, from one the learner knows) and `kin:` (the same shape in other topics). Checked by web search on 2026-10-24.
- **Fewer words, labels on the picture.** Coherence principle (leave out extraneous words and pictures): supported in 23 of 23 experimental tests, median effect size 0.86, per Mayer & Fiorella's chapter in the *Cambridge Handbook of Multimedia Learning* (2nd ed., 2014; an earlier count was 10 of 11 tests, median 1.32). Spatial contiguity (put words next to the part of the picture they describe): Ginns (2006), *Learning and Instruction* 16, 511–525, a meta-analysis of spatial and temporal contiguity. Hence the word limits, captions that say where to look, and term names under the formula. These are lab effects on short lessons; none tested viz-os.
Uncertainty: these are lab and classroom effects on average; none tested viz-os itself. The honest test is whether decks built with the probe and bridges beat decks without them for this learner, with the same topics.

## Size (measured at 2.0.0 with `wc -w`)
What the agent reads: `SKILL.md` 1,506 words (every time) · `probe.md` 1,059 (first turn) · `story.md` 2,778 and `spec.md` 4,789 (build turn). Example decks: `gallery` 2,231 words of YAML, `negative-binomial` 2,645, `mageck-rra` 3,891 for 30 slides. The kit (about 240 KB) is never read by the agent. Build and check print one line per problem.

## Backlog
- A cold-start test: a fresh agent with only the plugin builds a deck on a new topic, and the four gates plus a review score it. This is the real measure of whether the docs are enough.
- A light theme: it needs its own series palette, measured the same way on a light plate, and a full check run on all examples.
- Animated transitions between two states of the same chart (morphing marks), not just fades.
- Speaker notes / narration export, and an Obsidian companion note writer (the user's vault has an ingest script).
- Calc steps that follow sliders already recompute; tables do not yet take slider-driven rows.
- A tiny Python port of the expression language, so build-time lint can evaluate values (today it checks names and functions only; values are checked in the browser).
- A script that compares `numbers.txt` with `data.json` directly, instead of by eye.
