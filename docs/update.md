# UPDATE

In this repo, the user can say **UPDATE**. This authorizes preparing, committing and publishing the intended viz-os changes and updating its existing local installations. Preserve unrelated edits. No new CLI installs/upgrades, credentials, other plugins or external reviews are authorized. Use scripts for routine work, without model calls or delegation. A required cold start follows `testing.md` and the user's model/delegation authorization; do not substitute models. Read only failures and affected source, rather than entire logs or previous conversations.

1. Run `python3 tools/update.py status --refresh`. It prints the candidate, freshly fetched `origin/main`, pending commits and installed state. Review the full pending commit range and working diff; exclude unrelated commits. If HEAD is already published and release inputs are unchanged, go straight to step 5: no version bump, full regression or new cold start.
2. For new changes, review the implementation and choose a semantic version: major if previously valid lesson YAML can break. Write short release notes to `out/update/notes.md`, then run `python3 tools/update.py prepare --version X.Y.Z --notes out/update/notes.md` to synchronize all five manifests and changelog. Rebuild any affected tracked deck HTML. Inspect and commit only intended paths; never `git add -A`. Tools/docs-only changes need no plugin version bump. Keep unrelated dirty files out of the commit.
3. Run `python3 tools/update.py check`. This checks an archive of committed HEAD: updater fixture tests, the full regression and all five native validators, with no live installs. Detailed logs, browser contact sheets and successful-check records stay under `out/update/`. Checks are reused only for the identical candidate and environment, with an intact log. A failure or missing validator blocks publication. Review native validator warnings: exit zero alone does not settle their meaning. If tracked rebuilt HTML differs, rebuild it in the source and commit it before retrying.
4. Judge the applicable gates in `testing.md`: review implementation and release notes; inspect contact sheets after kit/example changes; independently verify numbers after skill code/data changes; run and judge a cold start after skill instruction changes. Passing scripts cannot supply these judgments. Write a short evidence note under `out/update/`, then a JSON file such as:

   ```json
   {"candidate":"FULL_HEAD_SHA","base":"FULL_FETCHED_MAIN_SHA","implementation":"/absolute/path/review.md","release_notes":"/absolute/path/review.md","eyes":"/absolute/path/review.md","numbers":"/absolute/path/review.md","cold_start":"/absolute/path/review.md"}
   ```

   Omit inapplicable gates. Values name real evidence files; one note can cover several gates, with artifact paths and actual findings. Run `python3 tools/update.py review --base BASE_SHA --evidence out/update/evidence.json`, then `python3 tools/update.py publish --base BASE_SHA`. Publication checks exact-candidate results/review, version advancement, remote identity and a forward-only main update. If source, environment, evidence or remote changes, reconcile and rerun the affected step. No forced push or branch reset.
5. Run `python3 tools/update.py install --candidate PUBLISHED_SHA`. Only exact current `origin/main` is accepted. It audits registrations and all tracked plugin files, updates stale existing targets through supported manager commands, verifies again and saves per-target results. Correct targets are skipped; repeat to resume failures. Missing installations stay absent; disabled ones stay disabled and need an explicit decision. The shared release clone must exist, be clean and on main; it advances only to the pinned commit. T3 uses the ownership-preserving helper after Antigravity verification. Muse uses its supported local-source install from that clone, preserving its marketplace and data. No cache or registry is edited directly.

The personal update targets are Claude, Codex, Grok, Muse, Antigravity, Gemini and T3. Cursor is excluded at the user's request and cannot block completion. Keep its package manifest synchronized for compatibility; do not inspect or update its installation. T3 plugin links do not prove model runtime discovery. Restart sessions after changes; runtime loading is **not tested** unless separately observed.

Output is short; logs and JSON records are in ignored `out/update/`. A user-wide lock prevents overlapping check, prepare, publish and install operations. Install exit 0 means inspected targets passed or were absent, not a model-runtime test; exit 2 means manual, disabled or failed targets remain. End with the published version/commit, qualifications and relevant log link. Automation cannot establish teaching quality or eliminate every possible failure.
